# Glitch control protocol (Renderer ↔ Brain)

Source of truth for the WebSocket message contract between the Renderer and the Brain.
Both sides must only send message types listed here — nothing undocumented.

**Direction:** the Brain hosts the WebSocket server; the Renderer is always the client, connecting
out to whatever `ws://<host>:<port>` it's configured with (same-machine or LAN, just a config
value on both sides) — browser JS can only open outbound
WebSocket connections, it cannot listen for them.

**Transport:** one JSON object per WebSocket text frame. Every message has a `type` field.

**Hard rule:** the Renderer never makes decisions. It only executes commands sent to it and
reports state/events back. All "thinking" happens in the Brain.

## Brain → Renderer

| `type` | Fields | Meaning |
|---|---|---|
| `ping` | — | Liveness check. Renderer replies with `pong`. |
| `set_expression` | `name: string`, `weight: number` (0–1) | Blend a VRM expression preset toward `weight`. Brain sends this once per reply for mood (`happy`/`angry`/`sad`/`relaxed`/`surprised`/`neutral` -- extracted from the `[mood: ...]` tag the LLM is prompted to start every reply with, stripped before it reaches `speak_text`/TTS). The Renderer treats these five as mutually exclusive (setting one fades the others to 0) and `neutral` as "fade all of them to 0" rather than a settable expression of its own. |
| `speak_text` | `text: string`, `partial?: bool`, `reach_out?: bool` | Her reply's text. While she's writing it, each sentence comes as soon as it's complete with `partial: true` (the Renderer grows one History bubble from them); then one without `partial` carries the whole reply, settles the bubble and ends the wait for a reply. Also sent unprompted, to every connected device, when she reaches out after a quiet spell (curiosity) -- then with `reach_out: true`, so a device waiting on its own reply keeps waiting. Not streamed when the model doesn't open its reply with its mood tag (or isn't streamed, e.g. Ollama or a harness): its sentences then come all at once. |
| `speak_audio` | `audio_b64: string`, `sample_rate: number`, `text: string`, `frames: [{t: number, shape: string, weight: number}]` | One clip of her voice -- a sentence of her reply, base64-encoded WAV -- with the `text` it says (its subtitle) and its lipsync keyframes (`t` in seconds from the clip's start). The Renderer queues each clip to start the moment the one before ends. After she's talked over (`speech_interrupted`) or a new message arrives, Brain stops sending the rest. |
| `profiles` | `names: [string]`, `active: string` | The current list of saved role-play profile names (from `brain/profiles/*.md`), and which one is currently selected (never `"Default"`, the reserved never-a-file entry the Renderer always offers alongside these -- see `load_profile`/`delete_profile`). Sent once right after `ready`, and again after every `save_profile`/`delete_profile`. |
| `profile_content` | `name: string`, `content: string` | The content of the named profile, in reply to `get_profile` -- used to pre-fill the profile editor when the user clicks Edit. |
| `souls` | `names: [string]`, `active: string` | The current list of saved soul names (from `brain/souls/*.md`) -- who Glitch is, as opposed to `profiles`' user role-play context -- and which one is currently selected (never `"Default"`, same reserved entry as profiles). Sent once right after `ready`, and again after every `save_soul`/`delete_soul`. |
| `topics` | `items: [string]` | The things she loves, from her main soul's "What you love" section (minus the user) and general conversation starters (goals, wishes, hobbies...), for the chat box's rotating "Talk about ..." hint. Sent once right after `ready`, and again after `save_soul_and_user`. |
| `soul_content` | `name: string`, `description: string`, `examples: string` | The named soul's content, split back into its two editor fields, in reply to `get_soul`. |
| `soul_and_user_content` | `soul: string`, `user: string` | The raw, currently-active `brain/soul.md`/`brain/user.md` content, in reply to `get_soul_and_user` -- for the Settings' manual-edit escape hatch, separate from `soul_content`/`profile_content` which are keyed by a saved name. `soul` is her permanent main `soul.md`, not the selected role-play soul. `user` is the main `user.md`, not the selected role-play profile. That `user.md` is also what she reads about the user in her prompt, every turn, whenever role-play is off (capped at 4000 chars). |
| `notes_content` | `content: string` | The raw current content of `brain/notes.md`, in reply to `get_notes` -- for the Settings' Notes editor. |
| `avatars` | `avatars: [{name: string, kind: string}]` | The list of installed *custom* avatars (from `brain/avatars/*.vrm`/`*.png`), each tagged `kind: "vrm"` or `"png"` -- does not include `"Glitch"`, the shipped default (always `"vrm"`) the Renderer always offers locally without needing Brain at all. Sent once right after `ready`, and again after every `save_avatar`. |
| `chat_logs` | `mode: string`, `days: [{date, size}]` | That mode's daily chat logs (`brain/chat_logs/`, role-play in `chat_logs/roleplay/`), newest first. |
| `chat_log_content` | `mode`, `date`, `content: string`, `error: string` | One day's log as saved (Markdown), or `error` if it can't be read. |
| `avatar_data` | `name: string`, `data_b64: string`, `kind: string` | Base64-encoded bytes for the named avatar, plus which kind it is (`"vrm"` or `"png"`) so the Renderer knows whether to parse it as a 3D model or just display it as a flat image (and disable camera panning for the latter -- see `main.js`'s `setActiveAvatar`). Sent in reply to `load_avatar` for any non-default name, and pushed automatically right after `ready` if the remembered active avatar is a custom one, so a reconnecting Renderer knows to swap to it instead of staying on the default it just booted with. |
| `backgrounds` | `names: [string]`, `active: string` | Settings -> Background's saved pictures (`brain/backgrounds.py`) and the one in use (`""` for none: the UI style's own backdrop). Sent after `ready`, and to every device after any change; a refused change answers only the asker. |
| `background_data` | `name: string`, `data_b64: string`, `kind: "png"\|"jpg"\|"webp"` | The background in use, shown behind her. Follows `backgrounds` whenever one is active, to every device, so all show the same. |
| `roleplay_state` | `active: bool` | Whether the selected profile is currently being applied. Sent once right after `ready`, and again after every `set_roleplay_active`, so the Renderer's toggle reflects Brain's persisted state rather than assuming a default. |
| `roleplay_engine` | `name: string` | The engine role-play switches to, or `""` to keep the current one. Sent after `ready` and to every device after `set_roleplay_engine`. A deleted engine reads as `""`. |
| `voice_state` | `active: bool` | Whether Glitch's spoken voice (TTS) is currently on. Sent once right after `ready` so the settings toggle reflects Brain's persisted state (`brain/voice_active.txt`) rather than assuming a default. |
| `web_search_state` | `active: bool` | Whether Glitch's own LLM path (`brain/web_search.py`, not a Hermes harness -- it already has its own web/session search when active) can search the web via tool-calling. Sent once right after `ready`, same pattern as `voice_state`. Always `false` if no SearXNG instance was ever configured (`config.yaml`'s `brain.web_search` block), regardless of what was saved. |
| `curiosity_state` | `active: bool` | Whether curiosity (`brain/curiosity.py`) is on: standing guidance to ask the odd follow-up, plus a short list of things she's wondered about the user, at most one worked into a reply every few turns. Sent once right after `ready`. Off during role-play regardless. |
| `curiosity_timer` | `state: string`, `due_at: float \| null`, `error: string` | Settings -> Curiosity's countdown: `"counting"` with `due_at` (epoch seconds when she may reach out), `"waiting"` (she reached out and waits for a reply), or paused: `"off"`, `"roleplay"`, `"harness"`. Sent on `ready`, after each user message, Clear Chat, a reach-out or a curiosity toggle, and whenever it changes (checked each minute). With `error`, only to the device whose `test_reach_out` couldn't run. |
| `sampling_state` | `active: string`, `profiles: {name: {temperature?, top_p?, top_k?, min_p?, presence_penalty?, repeat_penalty?}}`, `builtin: [string]`, `error: string` | Her sampling profiles (`brain/sampling.py`): the settings sent with each of her replies (never with the background calls), by profile name, and which one is `active`. A setting missing from a profile isn't sent, so the LLM server's own value is used. `builtin` names can't be saved over or deleted. Sent after `ready` and to every device after a change; a refused change is answered only to the sender, with `error` saying why. |
| `context_usage` | `used: int`, `window: int \| null`, `conversation: int \| null`, `keep: int \| null` | How full her context is, for the Settings meter: tokens after the latest reply (prompt + reply) out of the model's context size (`null` if the server doesn't report it), and the running conversation (estimated tokens, counted the way the trim counts them) out of how much she keeps. She keeps conversation up to about half of the context; past that the oldest part is dropped in one go. Sent after each reply, and after `ready` once there has been one. |
| `conversation_cleared` | -- | Sent to every device after `clear_conversation`: she's on a fresh conversation, so each clears its chat panel. |
| `training_state` | `available: bool`, `active: bool`, `pending: [{id, fact, source, created}]`, `error: str` | Memory training (`brain/training.py`): while `active` (and the memory provider is a configured Hindsight server -- `available`), nothing is retained on its own; once a night she proposes a few facts from the day's chat log into `pending` for the user to review (`source` names the day). Sent after `ready` and to every device after any change. `error` is `""` unless the last approval failed (the proposal then stays queued). |
| `lessons_state` | `available: bool`, `active: bool`, `autonomy: string`, `lessons: [{id, name, content, priority}]`, `pending: [{id, action, target_id, target_name, name, content, reason}]`, `error: string` | Everything the Settings panel's Behavior learning section shows. Sent on `ready` (as its own background task so an unreachable Hindsight can't delay the handshake) and broadcast to every device after any lesson/proposal/setting change. `available` is false unless the memory provider is a configured Hindsight server -- lessons are Hindsight directives, stored in a separate `<bank>-lessons` bank so Clear Memory can't wipe them. `error` is "" unless the lessons store couldn't be reached. |
| `lesson_event` | `kind: "applied" \| "proposed" \| "noted" \| "error"`, `text: string` | A one-line notice that a rating changed (or queued a change to) her lessons. The Renderer shows a toast, plus a system entry in the chat history for everything except `error`. `noted` means a possible new lesson was seen once and is waiting to be seen again (autonomy `all` only). |
| `memory_state` | `active: bool` | Whether Glitch's own native memory of the user (`brain/memory.py`) is currently on. Sent once right after `ready`, same reasoning as `voice_state`. Entirely separate from anything Hermes remembers on its own when the harness is active -- this only ever applies to her own personality (not `HarnessLLM`). |
| `memory_profiles` | `profiles: [{name, type}]`, `active: string`, `types: [{type, label, space_label, default_space}]`, `error: string` | Settings -> Memory backend (`brain/memory_profiles.py`): the saved memory servers (`type` is `"hindsight"`), which backend is active (`"Local file"` is the built-in one and never in `profiles`), and the kinds of server that can be added. Sent on `ready` and to every device after any change. With a non-empty `error`, sent only to the device whose request was refused or whose server couldn't be reached (a profile that can't be reached is still active; memory calls fail softly). |
| `memory_profile_content` | `name: string`, `profile: {type, url, api_key, space}` | One saved profile for the ✏️ editor, in reply to `get_memory_profile` (`profile` is `{}` if there's no such one). `space` is the Hindsight bank. `api_key` is echoed back the same way a saved LLM engine's is. |
| `memory_content` | `entries: list[string]` | Reply to `get_memory_content` -- the raw list of remembered facts, one per entry, for the settings panel's download button. |
| `memory_learned` | `fact: string` | Sent right when the local memory file gains a new fact (`brain/learning.py`); the Renderer shows a brief toast and a chat-history entry. Never sent for a memory server: Hindsight decides server-side what to keep and doesn't hand back the fact it extracted. |
| `thinking` | `tokens: number` | She's still thinking before her reply starts: how many tokens of thinking so far, every 50 or so (only from an LLM that streams its thinking, like LM Studio). The Renderer shows it in place of "processing" until her first sentence arrives. Only to the device that asked. |
| `no_reply` | -- | Sent instead of `speak_text` when Brain decided there's genuinely nothing to reply to -- empty `user_text`, or a `user_audio` whose transcription came back blank (e.g. silence). Lets the Renderer clear its "awaiting a reply" state (Send/camera/desktop/mic re-enable) without a blank chat-history entry, which `speak_text` with empty text would otherwise leave behind. |
| `user_transcript` | `text: string` | What STT heard in a `user_audio`, replacing its History bubble's "🎤 (voice message)" placeholder. Not sent for silence -- that's `no_reply`. |
| `left_off` | `note: string` | Her note on where the conversation just cleared left off -- written after `clear_conversation` (her own conversations only, not role-play or a harness), kept in her prompt for the next conversation, and broadcast so the Renderer can show it in the chat history. |
| `tts_engines` | `names: [string]`, `active: string` | The current list of saved speech-engine names (from `brain/tts_engines/*.json`), and which one is currently selected (never `"None"`, the reserved entry -- see `load_tts_engine`/`delete_tts_engine`). Sent once right after `ready`, and again after every `save_tts_engine`/`delete_tts_engine`. |
| `tts_engine_content` | `name: string`, `endpoint: string`, `api_key: string`, `voice: string`, `voices_dir: string`, `model: string` | The named engine's saved endpoint/api_key/voice/voices_dir/model, in reply to `get_tts_engine` -- used to pre-fill the speech-engine editor when the user clicks Edit. `voices_dir` is only meaningful for a Kokoro-fastapi-shaped engine (see `kokoro_voices.py`) -- `""` for anything else. `model` is the value sent as `/v1/audio/speech`'s `model` field (blank falls back to `RemoteTTS.DEFAULT_MODEL`, `"kokoro"` -- a real HTTP TTS server that isn't Kokoro-shaped needs this set explicitly). |
| `tts_voices` | `name: string`, `voices: [string]`, `active_voice: string`, `can_create_voice: bool`, `error: string` | Which custom voices have been created (by blending existing ones) for the named speech engine (`kokoro_voices.py`), its current default, and whether creating another is even possible for it (`voices_dir` configured). Everything empty/false for `"None"` or a name that isn't a real saved engine -- not an error, just nothing to show. `error` is `""` on every normal reply, set only when `combine_kokoro_voice` was refused. Sent once right after `ready` (for the active engine), and again after every `get_tts_voices`/`set_tts_voice`/`combine_kokoro_voice`. |
| `llm_engines` | `names: [string]`, `active: string` | The current list of saved LLM engine names (from `brain/llm_engines/*.json`), and which one is currently selected (never `"Default"`, the reserved entry meaning `config.yaml`'s own `brain.llm` block -- see `load_llm_engine`/`delete_llm_engine`). Sent once right after `ready`, and again after every `save_llm_engine`/`delete_llm_engine`. |
| `llm_engine_content` | `name: string`, `endpoint: string`, `model: string`, `api_key: string` | The named engine's saved endpoint/model/api_key, in reply to `get_llm_engine` -- used to pre-fill the LLM editor when the user clicks Edit. |
| `harness_state` | `active: bool`, `name: string`, `selected: string`, `available: [string]` | Whether Glitch is currently plugged into an external agent harness (`brain/harness.py`) instead of her own profile/soul/LLM engine, which one is actually connected (`name`, `""` if inactive), which one the dropdown should show as picked (`selected` -- the connected one while active, otherwise the last harness ever successfully turned on, so switching the harness off doesn't also make the Renderer forget the pick), and the open-ended list of harnesses the user has saved (`available`, from `brain/harnesses/*.json` -- not a fixed set). Sent once right after `ready`, and again after every `set_harness_active`/`save_harness`/`delete_harness` -- including a refused activation attempt, so the Renderer's toggle can resync to what Brain actually did rather than trusting its own optimistic guess. |
| `harness_content` | `name: string`, `endpoint: string`, `model: string`, `api_key: string` | The named harness's saved settings, in reply to `get_harness` -- pre-fills the harness editor for the Edit button. |
| `harness_health` | `name: string`, `reachable: bool \| null` | Whether that saved harness's endpoint answers a TCP check (`brain/health.py`), for its status light: `null` if it has no endpoint at all (a different light from `false`, set up but down). Sent after `ready`, and to every device whenever it changes (checked every 20 s). |
| `tts_health` | `name: string`, `reachable: bool \| null` | Same as `harness_health`, for a saved speech engine (never `"None"`). |
| `llm_models` | `endpoint: string`, `models: [string]` | The model IDs the given endpoint currently has loaded (`GET /v1/models`), in reply to `get_llm_models` -- populates the LLM editor's model field so the user can pick a real value instead of guessing one. `endpoint` is echoed back so the Renderer can discard a reply for an endpoint the user has since changed in the still-open editor. `models` is `[]` if the endpoint couldn't be reached at all (not fatal -- the field stays a free-text input either way). |
| `debug_pong` | `ts` (echoed back unchanged) | Reply to `debug_ping`, only sent while the Settings panel's Debugging toggle is on. `ts` is whatever the Renderer's own `debug_ping` sent -- Brain never interprets it, just echoes it back so the Renderer can compute round-trip time itself (`Date.now() - ts`). |
| `debug_event` | `category: string`, `message: string`, `ms: number` (optional) | A timing/outcome line for the Debugging log -- e.g. `category: "llm"`, `message: "LLM reply received"`, `ms: 842.3`. Only ever sent to a connection that's turned debugging on (`set_debug_active`), and only ever describes Brain's own external calls (LLM/TTS/STT/harness connect-disconnect/engine switches) -- **never** conversation content (no `message`/`speak_text` text, no profile/soul content). `ms` is omitted for events with no meaningful duration (e.g. a harness activation refused before any call was even attempted). |

## Renderer → Brain

| `type` | Fields | Meaning |
|---|---|---|
| `pong` | — | Reply to `ping`. |
| `ready` | `model: string`, `token: string` (optional), `device: string` (optional) | `device` is a plain description of the device ("Android phone · Chrome 140"), used only by the debug log to list connected devices and say which one did what. Sent once, right after the Renderer connects and the `.vrm` model has finished loading. `token` is only checked when the Brain has `brain.auth_token` configured (config.yaml) -- see "Authentication" below. Must be the connection's very first message when a token is configured; every other message type is refused until this one succeeds. |
| `error` | `message: string` | Something went wrong Renderer-side (e.g. failed to load the model) — reported, not acted on locally. |
| `user_text` | `text: string`, `image_b64: string` (optional), `image_mime: string` (optional, default `image/jpeg`) | The user typed a message (chat box), optionally with a camera/desktop snapshot attached (`text` may be empty when an image is attached -- Brain fills in a default prompt). When an image is present, Brain sends it to the LLM as a standard multimodal `image_url` content part; a non-vision-capable model/endpoint fails the same way a bad model string does (surfaced as a `speak_text` stand-in), not a separate error path. |
| `user_audio` | `audio_b64: string`, `mime_type: string` | Push-to-talk mic recording -- transcribed Brain-side (STT) and handled exactly like `user_text` once transcribed. |
| `regenerate_last` | `text: string`, `edited?: bool` | Re-answer the most recent prompt in place -- the Renderer's per-bubble retry (↻) and History panel's Resend Last both send this instead of a plain `user_text` when retrying the *latest* exchange, so the stale reply doesn't linger in context alongside a duplicated question. For `LocalLLM`/`OllamaLLM`, Brain pops the matching turn from its own conversation history first (`llm.py`'s `pop_last_exchange`, preferred over `text` when it finds one to pop) and then answers fresh, exactly as if asking for the first time; a `HarnessLLM` has no local history to pop, so this falls back to answering whatever `text` the Renderer sent, same as an ordinary `user_text`. Replies the same way `user_text` does (`speak_text`/`no_reply`/etc, no new response type). With `edited: true` (the ✏️ button), she answers `text` -- the user's corrected message -- instead of the original. |
| `delete_last` | `answered: bool` | The 🗑️ on the user's latest message (a mis-send, an accidental camera shot): Brain drops that turn from her conversation, plus her reply when `answered` (the Renderer showed one). Only pops if the tail matches `answered`, so a Stop that landed before the turn reached her history can't take an older exchange with it. A no-op with a harness or NoneLLM. |
| `clear_conversation` | -- | The Clear Chat button: she starts a fresh conversation (the running conversation and its saved copy are cleared; long-term memory is not). A reply still in flight is discarded. Answered with a `conversation_cleared` broadcast. |
| `stop_reply` | -- | Cancel the reply currently being generated (the Renderer's Stop button inside the chat box, shown only while it's waiting on a reply). Brain cancels the in-flight reply task and, for `LocalLLM`/`OllamaLLM`, discards whatever the LLM eventually returns instead of appending it to conversation history (the request itself can't be aborted mid-flight, so it may still finish in the background). Nothing is sent back -- the Renderer un-greys its input immediately. The stopped prompt stays in history as a dangling user turn, same shape as a failed request, so Resend Last still re-answers the right prompt. |
| `speech_interrupted` | `heard: number` (0–1) | The user talked over her (pressed 🎤 or sent a message) while her reply was playing; `heard` is how much of its audio had played. Brain cuts her latest reply in her conversation to about that share of its words, ending in " —", so she knows where she was stopped. No reply is sent. |
| `save_profile` | `name: string`, `content: string` | Create/overwrite a saved role-play profile -- `content` is one freeform markdown blob (character + scenario together), written to `brain/profiles/<name>.md`. Brain replies with an updated `profiles` list. |
| `load_profile` | `name: string` | Select the named saved profile (or `"Default"`, the reserved always-available entry meaning "no profile" -- clears `brain/user.md` instead of reading a file). Content is copied into `brain/user.md` regardless of the role-play toggle below. If role-play is currently active, it's also immediately folded into the system prompt for every subsequent reply (and conversation history is reset -- a new profile shouldn't continue an old exchange under the previous one's premise). If role-play is off, the selection is just remembered for whenever it's turned back on. Loading copies the profile into `brain/rp_user.md` -- the selected *role-play* profile -- and never touches `brain/user.md`, the user's own main file. |
| `get_profile` | `name: string` | Request the named profile's content, to pre-fill the profile editor for the Edit button (`save_profile` under the same name overwrites it once the user saves). Brain replies with `profile_content`. |
| `delete_profile` | `name: string` | Delete a saved profile -- removes `brain/profiles/<name>.md`. Refused for `"Default"` (not a real file, must always stay selectable). If the deleted profile was the active one, Brain falls back to `"Default"` (clearing `user.md`, and updating the LLM's persona if role-play is active) before replying with an updated `profiles` list. |
| `set_roleplay_active` | `active: bool`, `think?: bool` | Turn role-play on or off. Persisted (`brain/roleplay_active.txt`). On: if a role-play engine is set (`set_roleplay_engine`) and `think` is sent, Brain switches to that engine with thinking on/off as given, and switches back when role-play is turned off; with no role-play engine she stays on her current one. Either way her role-play scene is resumed, and turning it off brings the normal conversation back. Answered with `roleplay_state` and `llm_engines` broadcasts. |
| `set_roleplay_engine` | `name: string` | The saved LLM engine role-play switches to, or `""` to keep the current engine (the default). Answered with a `roleplay_engine` broadcast. |
| `set_voice_active` | `active: bool` | Turn Glitch's spoken voice on or off. `false` doesn't silence her -- every reply still arrives as `speak_text` (subtitle/mood keep working) -- it just skips TTS synthesis, so no `speak_audio` is sent for that reply. Persisted (`brain/voice_active.txt`) so it survives a Brain restart. Answered with a `voice_state` broadcast, so every device's toggle follows. |
| `set_web_search_active` | `active: bool` | Turn Glitch's own web-search tool on or off (`brain/web_search.py`). Persisted (`brain/web_search_active.txt`). Answered with a `web_search_state` broadcast. |
| `set_curiosity_active` | `active: bool` | Turns curiosity on/off. On by default. Answered with a `curiosity_state` broadcast. |
| `test_reach_out` | *(none)* | Settings -> Curiosity's Test button: she reaches out right now (a check-in; saved questions are kept for the real thing), then waits for a reply like after any reach-out. Refused (with a `curiosity_timer` error) during role-play, with a harness in control, or while a reply is in progress. |
| `set_sampling_profile` | `name: string` | Make a sampling profile the one her replies use. Answered with a `sampling_state` broadcast. |
| `save_sampling_profile` | `name: string`, `values: {temperature?, top_p?, top_k?, min_p?, presence_penalty?, repeat_penalty?}` | Save (or overwrite) a profile and make it active. Blank values are left out; out-of-range values are refused. Built-in names are refused. |
| `delete_sampling_profile` | `name: string` | Delete a saved profile; if it was active, the default takes over. Built-in profiles are refused. |
| `set_training_active` | `active: bool` | Turns memory training on/off. Off by default. Answered with a `training_state` broadcast. |
| `resolve_memory_proposal` | `id: str`, `approve: bool`, `fact?: str`, `importance?: "core"\|"normal"\|"minor"` | Approve (retaining `fact` -- the user's edited wording -- to Hindsight tagged `importance:<level>`; `core` facts are recalled into her prompt every turn) or reject one pending memory. Answered with a `training_state` broadcast. |
| `rate_reply` | `rating: "up" \| "down"`, `note?: string`, `user_text: string`, `reply_text: string` | A thumbs up/down on one of her replies (the Renderer's 👍/👎 on a history bubble, or the over-avatar mode's buttons for the latest reply). `note` is the optional reason -- "what should she do differently" for a 👎, "what did you like" for a 👍. Without one, Brain still logs the rating but can only use it to strengthen or weaken a lesson that already exists; it never creates, revises or retires one from a bare rating. Brain always appends it to a local ratings log (`brain/ratings_log.jsonl`, gitignored); it only *learns* from it -- a background LLM call that proposes, applies or queues a lesson (see `lesson_event`/`lessons_state`) -- when Behavior learning is on, role-play is off, and the LLM is a `LocalLLM`/`OllamaLLM`. Nothing is sent back for the rating itself. |

## Authentication

When `brain.auth_token` is set in `config.yaml`, the connection's first message must be `ready`
carrying a matching `token` field -- every other message type is refused (the connection is closed)
until that succeeds. This exists because the Brain has no other access control: anyone who can open
a WebSocket connection to it can chat as the user, rewrite Glitch's active persona, or fill disk
with uploaded avatars, so a token is required whenever `host` is anything other than
`localhost`/`127.0.0.1` (i.e. reachable from other devices on the LAN). See `brain/server.py`'s
`_authenticate`. Left unset, no token is checked at all -- fine for a strictly localhost-only setup
with nothing else able to reach the port.

## Adding a new message type

1. Add a row to the table above (this file is the source of truth, not the code).
2. Add it to `brain/protocol.py` (the shared schema Brain-side code builds/validates messages
   against).
3. Add the matching handler on the other side: Brain-side, a handler registered with
   `@hub.handles(protocol.X)` in the module that owns it; Renderer-side, an entry in that
   feature module's `handlers` (see `src/brain_client.js`).

Nothing sends or handles a message type that isn't documented here first.
