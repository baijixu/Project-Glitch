# Glitch control protocol (Renderer ↔ Brain)

Source of truth for the WebSocket message contract between the Renderer and the Brain (SPEC.md
section 6). Both sides must only send message types listed here — nothing undocumented.

**Direction:** the Brain hosts the WebSocket server; the Renderer is always the client, connecting
out to whatever `ws://<host>:<port>` it's configured with (same-machine or LAN, just a config
value on both sides). Fixed by SPEC.md section 5 — browser/WebView JS can only open outbound
WebSocket connections, it cannot listen for them.

**Transport:** one JSON object per WebSocket text frame. Every message has a `type` field.

**Hard rule:** the Renderer never makes decisions. It only executes commands sent to it and
reports state/events back. All "thinking" happens in the Brain.

## Brain → Renderer

| `type` | Fields | Meaning |
|---|---|---|
| `ping` | — | Liveness check. Renderer replies with `pong`. |
| `play_animation` | `name: string`, `loop: bool` | Play a named animation clip. |
| `set_expression` | `name: string`, `weight: number` (0–1) | Blend a VRM expression preset toward `weight`. Brain sends this once per reply for mood (`happy`/`angry`/`sad`/`relaxed`/`surprised`/`neutral` -- extracted from a `[mood: ...]` tag the LLM is prompted to end every reply with, stripped before it reaches `speak_text`/TTS). The Renderer treats these five as mutually exclusive (setting one fades the others to 0) and `neutral` as "fade all of them to 0" rather than a settable expression of its own. |
| `viseme_stream` | `frames: [{t: number, shape: string, weight: number}]` | Lipsync playback: a timed sequence of viseme shape/weight keyframes, `t` in seconds from stream start. |
| `speak_text` | `text: string` | The LLM's reply, to display as an on-screen subtitle. Sent alongside `speak_audio`/`viseme_stream` once TTS is in the loop -- audio playback is the real "she's speaking" signal, this is just the subtitle companion to it. |
| `speak_audio` | `audio_b64: string`, `sample_rate: number` | TTS output for the current reply -- base64-encoded WAV/PCM audio to play. Paired with a `viseme_stream` sent alongside it for lipsync timed to this same clip. |
| `profiles` | `names: [string]`, `active: string` | The current list of saved role-play profile names (from `brain/profiles/*.md`), and which one is currently selected (never `"Default"`, the reserved never-a-file entry the Renderer always offers alongside these -- see `load_profile`/`delete_profile`). Sent once right after `ready`, and again after every `save_profile`/`delete_profile`. |
| `profile_content` | `name: string`, `content: string` | The content of the named profile, in reply to `get_profile` -- used to pre-fill the profile editor when the user clicks Edit. |
| `souls` | `names: [string]`, `active: string` | The current list of saved soul names (from `brain/souls/*.md`) -- who Glitch is, as opposed to `profiles`' user role-play context -- and which one is currently selected (never `"Default"`, same reserved entry as profiles). Sent once right after `ready`, and again after every `save_soul`/`delete_soul`. |
| `soul_content` | `name: string`, `description: string`, `examples: string` | The named soul's content, split back into its two editor fields, in reply to `get_soul`. |
| `soul_and_user_content` | `soul: string`, `user: string` | The raw, currently-active `brain/soul.md`/`brain/user.md` content, in reply to `get_soul_and_user` -- for the Settings' manual-edit escape hatch, separate from `soul_content`/`profile_content` which are keyed by a saved name. |
| `notes_content` | `content: string` | The raw current content of `brain/notes.md`, in reply to `get_notes` -- for the Settings' Notes editor. |
| `avatars` | `avatars: [{name: string, kind: string}]` | The list of installed *custom* avatars (from `brain/avatars/*.vrm`/`*.png`), each tagged `kind: "vrm"` or `"png"` -- does not include `"Glitch"`, the shipped default (always `"vrm"`) the Renderer always offers locally without needing Brain at all. Sent once right after `ready`, and again after every `save_avatar`. |
| `avatar_data` | `name: string`, `data_b64: string`, `kind: string` | Base64-encoded bytes for the named avatar, plus which kind it is (`"vrm"` or `"png"`) so the Renderer knows whether to parse it as a 3D model or just display it as a flat image (and disable camera panning for the latter -- see `main.js`'s `setActiveAvatar`). Sent in reply to `load_avatar` for any non-default name, and pushed automatically right after `ready` if the remembered active avatar is a custom one, so a reconnecting Renderer knows to swap to it instead of staying on the default it just booted with. |
| `roleplay_state` | `active: bool` | Whether the selected profile is currently being applied. Sent once right after `ready`, and again after every `set_roleplay_active`, so the Renderer's toggle reflects Brain's persisted state rather than assuming a default. |
| `voice_state` | `active: bool` | Whether Glitch's spoken voice (TTS) is currently on. Sent once right after `ready` so the settings toggle reflects Brain's persisted state (`brain/voice_active.txt`) rather than assuming a default. |
| `memory_state` | `active: bool` | Whether Glitch's own native memory of the user (`brain/memory.py`) is currently on. Sent once right after `ready`, same reasoning as `voice_state`. Entirely separate from anything Hermes remembers on its own when the harness is active -- this only ever applies to her own personality (not `HarnessLLM`). |
| `memory_content` | `entries: list[string]` | Reply to `get_memory_content` -- the raw list of remembered facts, one per entry, for the settings panel's download button. |
| `memory_learned` | `fact: string` | Sent once, right when Glitch's native memory actually gains a new fact (never for a duplicate/no-op). Unlike `debug_event`, this is always sent regardless of the Debugging toggle -- the Renderer surfaces it as a brief toast and a chat-history entry. |
| `no_reply` | -- | Sent instead of `speak_text` when Brain decided there's genuinely nothing to reply to -- empty `user_text`, or a `user_audio` whose transcription came back blank (e.g. silence). Lets the Renderer clear its "awaiting a reply" state (Send/camera/desktop/mic re-enable) without a blank chat-history entry, which `speak_text` with empty text would otherwise leave behind. |
| `tts_engines` | `names: [string]`, `active: string` | The current list of saved speech-engine names (from `brain/tts_engines/*.json`), and which one is currently selected (never `"None"`, the reserved entry -- see `load_tts_engine`/`delete_tts_engine`). Sent once right after `ready`, and again after every `save_tts_engine`/`delete_tts_engine`. |
| `tts_engine_content` | `name: string`, `endpoint: string`, `api_key: string`, `voice: string`, `voices_dir: string`, `model: string` | The named engine's saved endpoint/api_key/voice/voices_dir/model, in reply to `get_tts_engine` -- used to pre-fill the speech-engine editor when the user clicks Edit. `voices_dir` is only meaningful for a Kokoro-fastapi-shaped engine (see `kokoro_voices.py`) -- `""` for anything else. `model` is the value sent as `/v1/audio/speech`'s `model` field (blank falls back to `RemoteTTS.DEFAULT_MODEL`, `"kokoro"` -- a real HTTP TTS server that isn't Kokoro-shaped needs this set explicitly). |
| `tts_voices` | `name: string`, `voices: [string]`, `active_voice: string`, `can_create_voice: bool`, `error: string` | Which custom voices have been created (by blending existing ones) for the named speech engine (`kokoro_voices.py`), its current default, and whether creating another is even possible for it (`voices_dir` configured). Everything empty/false for `"None"` or a name that isn't a real saved engine -- not an error, just nothing to show. `error` is `""` on every normal reply, set only when `combine_kokoro_voice` was refused. Sent once right after `ready` (for the active engine), and again after every `get_tts_voices`/`set_tts_voice`/`combine_kokoro_voice`. |
| `llm_engines` | `names: [string]`, `active: string` | The current list of saved LLM engine names (from `brain/llm_engines/*.json`), and which one is currently selected (never `"Default"`, the reserved entry meaning `config.yaml`'s own `brain.llm` block -- see `load_llm_engine`/`delete_llm_engine`). Sent once right after `ready`, and again after every `save_llm_engine`/`delete_llm_engine`. |
| `llm_engine_content` | `name: string`, `endpoint: string`, `model: string`, `api_key: string` | The named engine's saved endpoint/model/api_key, in reply to `get_llm_engine` -- used to pre-fill the LLM editor when the user clicks Edit. |
| `harness_state` | `active: bool`, `name: string`, `selected: string`, `available: [string]`, `switch_key: string` | Whether Glitch is currently plugged into an external agent harness (`brain/harness.py`) instead of her own profile/soul/LLM engine, which one is actually connected (`name`, `""` if inactive), which one the dropdown should show as picked (`selected` -- the connected one while active, otherwise the last harness ever successfully turned on, so switching the harness off doesn't also make the Renderer forget the pick), the open-ended list of harnesses the user has saved (`available`, from `brain/harnesses/*.json` -- not a fixed set), and the actual current harness-switch secret (`""` if none set) -- sent back the same way `tts_engine_content`/`llm_engine_content` echo back a saved `api_key`, so the Renderer can pre-fill the Harness settings' key field for editing *and* automatically include the current key on every subsequent `set_harness_active`, instead of the user retyping it on every connection attempt. Sent once right after `ready`, and again after every `set_harness_active`/`save_harness_key`/`save_harness`/`delete_harness` -- including a refused activation attempt, so the Renderer's toggle can resync to what Brain actually did rather than trusting its own optimistic guess. |
| `llm_models` | `endpoint: string`, `models: [string]` | The model IDs the given endpoint currently has loaded (`GET /v1/models`), in reply to `get_llm_models` -- populates the LLM editor's model field so the user can pick a real value instead of guessing one. `endpoint` is echoed back so the Renderer can discard a reply for an endpoint the user has since changed in the still-open editor. `models` is `[]` if the endpoint couldn't be reached at all (not fatal -- the field stays a free-text input either way). |
| `debug_pong` | `ts` (echoed back unchanged) | Reply to `debug_ping`, only sent while the Settings panel's Debugging toggle is on. `ts` is whatever the Renderer's own `debug_ping` sent -- Brain never interprets it, just echoes it back so the Renderer can compute round-trip time itself (`Date.now() - ts`). |
| `debug_event` | `category: string`, `message: string`, `ms: number` (optional) | A timing/outcome line for the Debugging log -- e.g. `category: "llm"`, `message: "LLM reply received"`, `ms: 842.3`. Only ever sent to a connection that's turned debugging on (`set_debug_active`), and only ever describes Brain's own external calls (LLM/TTS/STT/harness connect-disconnect/engine switches) -- **never** conversation content (no `message`/`speak_text` text, no profile/soul content). `ms` is omitted for events with no meaningful duration (e.g. a harness activation refused before any call was even attempted). |

## Renderer → Brain

| `type` | Fields | Meaning |
|---|---|---|
| `pong` | — | Reply to `ping`. |
| `ready` | `model: string`, `token: string` (optional) | Sent once, right after the Renderer connects and the `.vrm` model has finished loading. `token` is only checked when the Brain has `brain.auth_token` configured (config.yaml) -- see "Authentication" below. Must be the connection's very first message when a token is configured; every other message type is refused until this one succeeds. |
| `animation_finished` | `name: string` | The named `play_animation` clip completed. |
| `error` | `message: string` | Something went wrong Renderer-side (failed to load model, unknown animation name, etc.) — reported, not acted on locally. |
| `user_text` | `text: string`, `image_b64: string` (optional), `image_mime: string` (optional, default `image/jpeg`) | The user typed a message (chat box), optionally with a camera/desktop snapshot attached (`text` may be empty when an image is attached -- Brain fills in a default prompt). When an image is present, Brain sends it to the LLM as a standard multimodal `image_url` content part; a non-vision-capable model/endpoint fails the same way a bad model string does (surfaced as a `speak_text` stand-in), not a separate error path. |
| `user_audio` | `audio_b64: string`, `mime_type: string` | Push-to-talk mic recording -- transcribed Brain-side (STT) and handled exactly like `user_text` once transcribed. |
| `regenerate_last` | `text: string` | Re-answer the most recent prompt in place -- the Renderer's per-bubble retry (↻) and History panel's Resend Last both send this instead of a plain `user_text` when retrying the *latest* exchange, so the stale reply doesn't linger in context alongside a duplicated question. For `LocalLLM`/`OllamaLLM`, Brain pops the matching turn from its own conversation history first (`llm/client.py`'s `pop_last_exchange`, preferred over `text` when it finds one to pop) and then answers fresh, exactly as if asking for the first time; a `HarnessLLM` has no local history to pop, so this falls back to answering whatever `text` the Renderer sent, same as an ordinary `user_text`. Replies the same way `user_text` does (`speak_text`/`no_reply`/etc, no new response type). |
| `save_profile` | `name: string`, `content: string` | Create/overwrite a saved role-play profile -- `content` is one freeform markdown blob (character + scenario together), written to `brain/profiles/<name>.md`. Brain replies with an updated `profiles` list. |
| `load_profile` | `name: string` | Select the named saved profile (or `"Default"`, the reserved always-available entry meaning "no profile" -- clears `brain/user.md` instead of reading a file). Content is copied into `brain/user.md` regardless of the role-play toggle below. If role-play is currently active, it's also immediately folded into the system prompt for every subsequent reply (and conversation history is reset -- a new profile shouldn't continue an old exchange under the previous one's premise). If role-play is off, the selection is just remembered for whenever it's turned back on. |
| `get_profile` | `name: string` | Request the named profile's content, to pre-fill the profile editor for the Edit button (`save_profile` under the same name overwrites it once the user saves). Brain replies with `profile_content`. |
| `delete_profile` | `name: string` | Delete a saved profile -- removes `brain/profiles/<name>.md`. Refused for `"Default"` (not a real file, must always stay selectable). If the deleted profile was the active one, Brain falls back to `"Default"` (clearing `user.md`, and updating the LLM's persona if role-play is active) before replying with an updated `profiles` list. |
| `set_roleplay_active` | `active: bool` | Turn the selected profile's effect on the LLM on or off without losing the selection: `true` folds the currently-selected profile (if any) back into the system prompt (resets conversation history); `false` clears it so Glitch behaves according to her soul/default personality alone. Persisted (`brain/roleplay_active.txt`) so it survives a Brain restart. Brain replies with `roleplay_state`. |
| `set_voice_active` | `active: bool` | Turn Glitch's spoken voice on or off. `false` doesn't silence her -- every reply still arrives as `speak_text` (subtitle/mood keep working) -- it just skips TTS synthesis, so no `speak_audio`/`viseme_stream` is sent for that reply. Persisted (`brain/voice_active.txt`) so it survives a Brain restart. No reply is sent (the Renderer's own toggle already reflects the change it just made). |
| `set_memory_active` | `active: bool` | Turn Glitch's own native memory of the user on or off. Persisted (`brain/memory_active.txt`). No reply is sent, same reasoning as `set_voice_active`. |
| `clear_memory` | -- | Erases every remembered fact (`brain/memory.md`) and immediately clears it from the live LLM's system prompt too (no restart needed). No reply is sent. |
| `get_memory_content` | -- | Request the current remembered-facts list. Brain replies with `memory_content`. |
| `save_soul` | `name: string`, `description: string`, `examples: string` | Create/overwrite a saved soul -- who Glitch is (`description`) and example `<user>`/`<character>` dialogue turns (`examples`), kept as two separate fields (unlike `save_profile`'s single combined blob) so the editor can show and re-populate them as two distinct boxes. Written to `brain/souls/<name>.md`. Brain replies with an updated `souls` list. |
| `load_soul` | `name: string` | Make the named saved soul the active one (or `"Default"`, the reserved always-available entry meaning "no custom soul" -- clears `brain/soul.md`, which falls back to `DEFAULT_PERSONALITY`). Content is copied into `brain/soul.md` and replaces the LLM's default personality (not layered on top of it, the way a loaded profile is) for every subsequent reply. The mood-tag instruction stays fixed underneath regardless. Resets conversation history. |
| `get_soul` | `name: string` | Request the named soul's content, split back into its two fields, to pre-fill the soul editor for the Edit button. Brain replies with `soul_content`. |
| `delete_soul` | `name: string` | Delete a saved soul -- removes `brain/souls/<name>.md`. Refused for `"Default"` (not a real file, must always stay selectable). If the deleted soul was the active one, Brain falls back to `"Default"` (clearing `soul.md` and the LLM's soul) before replying with an updated `souls` list. |
| `get_soul_and_user` | -- | Request the raw, currently-active `soul.md`/`user.md` content for the Settings' manual-edit escape hatch. Brain replies with `soul_and_user_content`. |
| `save_soul_and_user` | `soul: string`, `user: string` | Directly overwrite `brain/soul.md`/`brain/user.md`, bypassing the named saved-soul/profile system entirely, then re-apply them to the live LLM the same way loading a saved soul/profile already does (soul unconditionally, user only while role-play is on). No reply. |
| `get_notes` | -- | Request the current content of `brain/notes.md` -- a free-form scratchpad for the user's own ideas/todos, never read by the LLM or included in any prompt. Brain replies with `notes_content`. |
| `save_notes` | `content: string` | Overwrite `brain/notes.md` with `content`. No reply. |
| `save_avatar` | `name: string`, `data_b64: string`, `kind: string` | Install a new avatar (the user's imported `.vrm` or `.png` file) -- `kind` (`"vrm"` or `"png"`, refused otherwise) picks the file extension, written to `brain/avatars/<name>.<kind>`, and made the active one. Saving over a name that previously existed as the other kind replaces it (a name is one avatar, not one slot per file type). The Renderer already has the raw bytes locally (it just read the file), so it swaps immediately client-side without waiting for a reply; Brain replies with an updated `avatars` list so the new one shows up for future sessions/other devices. |
| `load_avatar` | `name: string` | Make an already-installed avatar (or `"Glitch"`, the default) the active one. For `"Glitch"` this is bookkeeping only -- no reply, the Renderer loads it locally. For any other name, Brain reads the file and replies with `avatar_data` (which carries the saved `kind` -- the Renderer doesn't need to remember it itself). |
| `save_tts_engine` | `name: string`, `endpoint: string`, `api_key: string`, `voice: string`, `voices_dir: string`, `model: string` | Create/overwrite a saved speech engine -- `endpoint` is an OpenAI-compatible base URL (e.g. Kokoro run via `docker-compose.yml`'s `kokoro-tts` service, `http://localhost:8880/v1`), `api_key`/`voice`/`voices_dir`/`model` optional. `voice`/`model` are the values sent on every speech request (any engine can set these -- blank falls back to `RemoteTTS.DEFAULT_VOICE`/`DEFAULT_MODEL`); `voices_dir` is a local folder Brain can save a newly-blended custom voice into, only meaningful for a Kokoro-fastapi-shaped engine (see `kokoro_voices.py`). Written to `brain/tts_engines/<name>.json`, preserving whatever `custom_voices` that file already had. Brain replies with an updated `tts_engines` list. |
| `load_tts_engine` | `name: string` | Make the named saved engine (or `"None"`, the reserved entry meaning no speech at all -- see `tts_engines.py`'s `NONE_NAME`) the one used for every subsequent reply's speech. Falls back to `"None"` Brain-side if the named engine can't actually be reached/loaded. |
| `get_tts_engine` | `name: string` | Request the named engine's saved endpoint/api_key/voice/voices_dir/model, to pre-fill the speech-engine editor for the Edit button. Brain replies with `tts_engine_content`. |
| `delete_tts_engine` | `name: string` | Delete a saved speech engine -- removes `brain/tts_engines/<name>.json`. Refused for `"None"` (not a real file, must always stay selectable). If the deleted engine was the active one, Brain falls back to `"None"` before replying with an updated `tts_engines` list. |
| `get_tts_voices` | `name: string` | Ask which custom voices exist for the named speech engine and whether uploading is possible for it. Brain replies with `tts_voices`. |
| `set_tts_voice` | `name: string`, `voice: string` | Change a saved speech engine's default voice -- `voice: ""` clears it back to `RemoteTTS.DEFAULT_VOICE` (the Renderer's picker's "Default" entry). If `name` is the active engine, Brain rebuilds it immediately so the change takes effect on the next reply; otherwise only the saved file changes. Brain replies with `tts_voices`. |
| `combine_kokoro_voice` | `name: string`, `voice_name: string`, `spec: string` | Create a custom voice for a Kokoro-fastapi-shaped speech engine by blending existing ones -- `spec` is Kokoro's own blend syntax (e.g. `"af_sky(1)+af_bella(0.8)"`), passed straight through to that engine's own `POST /v1/audio/voices/combine` (`kokoro_voices.py`; requires that image's `ALLOW_LOCAL_VOICE_SAVING=true`, see `docker-compose.yml`). Refused if `name`'s saved engine has no `voices_dir` configured (nowhere for Brain to save the result). Written as `<voices_dir>/af_<sanitized voice_name>.pt` (every result is force-prefixed `af_` -- see `kokoro_voices.py` for why), then made that engine's new default voice the same way `set_tts_voice` would. Brain replies with `tts_voices`. |
| `save_llm_engine` | `name: string`, `endpoint: string`, `model: string`, `api_key: string` | Create/overwrite a saved LLM engine -- `endpoint` is an OpenAI-compatible base URL (LM Studio, llama-server, etc.), `model`/`api_key` optional (`model: ""` means "whatever the endpoint has loaded", same as `config.yaml`'s own `llm.model: null`). Written to `brain/llm_engines/<name>.json`. Brain replies with an updated `llm_engines` list. |
| `load_llm_engine` | `name: string` | Make the named saved engine (or `"Default"`, the reserved entry meaning `config.yaml`'s own `brain.llm` block) the one used for every subsequent reply. Rebuilds Brain's `LocalLLM` instance and re-primes it with whatever soul/profile is currently active (conversation history resets, same as a soul/profile change). Falls back to `"Default"` Brain-side if the named engine's saved config can't be read. |
| `get_llm_models` | `endpoint: string`, `api_key: string` (optional) | Ask Brain to query the given endpoint's `GET /v1/models` (not necessarily a saved engine yet -- whatever's currently typed in the editor) and report back what's actually loaded there. Brain replies with `llm_models`. |
| `get_llm_engine` | `name: string` | Request the named engine's saved endpoint/model/api_key, to pre-fill the LLM editor for the Edit button. Brain replies with `llm_engine_content`. |
| `delete_llm_engine` | `name: string` | Delete a saved LLM engine -- removes `brain/llm_engines/<name>.json`. Refused for `"Default"` (not a real file, must always stay selectable). If the deleted engine was the active one, Brain falls back to `"Default"` before replying with an updated `llm_engines` list. |
| `set_harness_active` | `active: bool`, `name: string`, `key: string` (only meaningful when `active` is `true`) | Plug Glitch into (`true`) or disconnect her from (`false`) the named agent harness (must be one of `harness_state`'s `available` list, e.g. `"Hermes"`). Turning one **on** additionally requires `key` to match the currently saved harness-switch secret when one's set (refused, silently from the Renderer's perspective beyond the `harness_state` reply, if it doesn't match or is missing) -- a second secret separate from the connection's own `auth_token`, gating only this specific escalation. The Renderer sends its own last-known `switch_key` (learned from a prior `harness_state`) automatically here -- the user only ever types it once, into the Harness settings' key field (see `save_harness_key`), not on every connection attempt. Turning one **off** never checks `key` at all. While active, Brain replaces her `LocalLLM` with a `HarnessLLM` (`brain/llm/client.py`) that sends the user's text straight to the harness's own OpenAI-compatible endpoint (`config.yaml`'s `brain.harness.<name>` block) with no system prompt of its own -- the harness's own agent/session *is* her personality now, her profile/soul/LLM-engine settings are bypassed entirely (not deleted, just unused) until this is turned back off. STT/TTS/viseme playback are unaffected either way -- only the reply-generation step changes. Brain always replies with the resulting `harness_state`, whether or not the request actually succeeded. |
| `select_harness` | `name: string` | Move the Renderer's harness dropdown pick without connecting to anything -- no `key` needed, unlike `set_harness_active`. Only meaningful while inactive (the dropdown is disabled while a harness is actually connected). Persists as `harness.py`'s `selected_harness_name` (`""` for `harness.NONE_NAME`) so a later refresh/reconnect shows the same pick instead of falling back to whatever was last actually connected -- see `harness_state`'s own `selected` field. Brain always replies with the resulting `harness_state`. |
| `save_harness_key` | `key: string` | Set (or, if `key` is `""`, clear) the secret required to turn a harness on -- persisted (`brain/harness_switch_key.txt`) so it survives a Brain restart. Any already-authenticated connection can call this, same trust level as every other settings-panel action. Brain replies with an updated `harness_state` so every connected Renderer (not just the one that saved it) learns the new value. |
| `set_debug_active` | `active: bool` | Turn the Settings panel's Debugging toggle on/off for *this connection only* -- Brain tracks which open connections currently want `debug_event`s (`main.py`'s `_DEBUG_CONNECTIONS`) rather than broadcasting them to every Renderer regardless of whether it asked. No reply -- the Renderer already knows its own toggle state; it's Brain's future sends that need to know this, not the client. |
| `debug_ping` | `ts` (opaque to Brain, echoed back unchanged) | A liveness/round-trip-time probe the Renderer sends periodically while debugging is on -- distinct from the existing Brain-initiated `ping`/`pong` (which only measures Brain's own send interval, not actual network RTT). Brain replies with `debug_pong` immediately. |
| `restart_brain` | — | Restart Brain's entire Python process in place (`os.execv` -- same PID, re-reads `config.yaml`, rebuilds every engine/soul/profile/harness from disk exactly like a normal launch). In-memory conversation history is lost, same as any other restart. No reply -- the process is gone before one could be sent; every connected Renderer just sees an ordinary disconnect and reconnects on its own (`brain_client.js`'s existing reconnect loop), getting a fresh `ready` handshake once the new process is listening again. |

**Transfer size note:** VRM files are large (the shipped default is ~15MB; base64 adds ~33% on top), so the WS server's `max_size` is set well above the default 20MB used for TTS/STT audio -- see `brain/main.py`.

## Authentication

When `brain.auth_token` is set in `config.yaml`, the connection's first message must be `ready`
carrying a matching `token` field -- every other message type is refused (the connection is closed)
until that succeeds. This exists because the Brain has no other access control: anyone who can open
a WebSocket connection to it can chat as the user, rewrite Glitch's active persona, or fill disk
with uploaded avatars, so a token is required whenever `host` is anything other than
`localhost`/`127.0.0.1` (i.e. reachable from other devices on the LAN). See `brain/main.py`'s
`_authenticate`. Left unset, no token is checked at all -- fine for a strictly localhost-only setup
with nothing else able to reach the port.

The harness-switch secret (set via `save_harness_key`, seeded from `config.yaml`'s
`brain.harness_switch_key` on a machine that's never saved one yet) is a second, separate secret
layered on top of the above -- it doesn't gate the connection itself, only `set_harness_active`'s
escalation into harness mode (see that row's own description above). A connection that's already
passed `auth_token` still needs this second key to turn a harness *on*; turning one off never
requires it. Unlike `auth_token`, the user only ever types this one once (into the Harness settings'
key field) -- every connected Renderer learns the current value from `harness_state` and resends it
automatically from then on, so Brain still validates a real match on every attempt without the user
retyping anything.

## Adding a new message type

1. Add a row to the table above (this file is the source of truth, not the code).
2. Add it to `brain/protocol.py` (the shared schema Brain-side code builds/validates messages
   against).
3. Add the matching handler on the other side (Renderer's `src/brain_client.js`, or the relevant
   Brain subsystem).

Nothing sends or handles a message type that isn't documented here first.
